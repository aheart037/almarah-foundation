# V2 Part 2 — Donation management implementation and validation

Branch: `v2-donation-management` from audited commit `b470a6a8de294b10e2808c03ad351912682d8e61`. Existing controllers, repositories, gateway adapters, email queue, financial reports and public payment return URLs were retained. This is **not** a production deployment.

## Completed in this branch

- Existing public card checkout continues through `fundraise-submit.php`/gateway adapters; it now captures optional acknowledgment recipient and referral metadata on the **existing donation**, and withholds the *official* receipt until staff verification. Public payment-success UI now distinguishes confirmed payment from an authorized receipt.
- New `/donate/transfer` is a **submission route for offline/online transfers**, not a replacement payment engine or duplicate donation page. Collects donor, amount, date, reference, notes, conditional recipient/referral fields and optional payment proof. Public cash claims are disallowed; staff can enter cash. Uses existing donors/donations and donor rate limiting. Staff's existing `/admin/finance/offline` form now uses the same reviewed intake. Anonymous staff gifts still supported; existing purpose, currency and monthly fields preserved.
- Private payment proof storage via existing `UploadService`: PDF/JPEG/PNG only, 5 MB, randomized name, MIME checks, non-public `storage/private`; authenticated `/admin/donations/{id}/proof` download. No proof file is treated as bank confirmation.
- Additive migration `0012_donation_review.sql` extends `donations` and adds **only one** append-only `donation_review_events` relation. Existing records default to `legacy`; all new records are `submitted`. `public_reference` remains a unique reference from submission; **official** `receipt_number` is issued only after final approval. New official number `R-<unique public_reference>` avoids sequence race, and generation time is stored. Historical records are not backfilled or relabeled as staff-verified.
- Configurable ordered stage map in `config/donation_review.php` defaults to initial reviewer → verification officer → finance manager → super admin (final). Two stage-specific roles seeded; all decisions persist identity, UTC time, stage, decision and comment. Server-side checks enforce role, sequential transitions, payment-provider completion for online finalization, distinct stage actors and no submitter self-approval. Database row locks serialize concurrent reviewers. Rejection requires a reason. Corrections to unverified references by super admin reset verification with durable history; existing audited finance adjustments remain for historical money changes, but cannot manually complete a new unverified donation or alter an already verified new amount.
- Existing admin donation listing and detail extended with verification/recipient/referral/transaction/staff information, search filters, duplicate-reference warnings (never hard-reject), proof access, review/staff/email histories, controlled correction and documents. Existing donation CSV enhanced with filters and spreadsheet-formula escaping.
- Staff-only branded PDF receipt, thank-you letter and authorized certificate generated with the repository's FPDF and logo resolver. No tax-exemption document is generated. On final verification the certificate is authorized and the existing PHPMailer queue receives an acknowledgment/receipt to the donor and, if provided, a separate acknowledgment to the recipient. New verified receipt jobs attach the receipt and certificate as in-memory PDFs; email queue retains attempts/failures. Staff finance resend creates a new audited delivery attempt. Gateways' existing legacy receipt behavior is retained.

## Database and deployment

Migration `database/migrations/0012_donation_review.sql` adds nullable transaction timestamp, method, private proof path, recipient/referral fields, reviewer/time, receipt generation time and certificate status; `verification_status` defaults to `legacy` on preexisting rows. Indexes on verification status, transaction reference, referrer, recipient, verifier; FK from `verified_by` and review events to existing users/donations. `RoleSeeder` adds initial reviewer/verification officer; `SiteContentSeeder` grants `dashboard.view` and `donations.view` to them. **Deploy migration before new PHP code**, then run existing `php bin/console db:seed`; grant newly seeded roles to appropriate staff accounts. Back up DB + uploads first; test migration and restore on a clone. Do not reorder stages while reviews are in progress without a state-mapping migration. Configure SMTP/queue/cron and upload permissions.

## Remaining limitations / approval boundaries

1. **No official tax-exemption document**: user indicated they will supply legal authorization, but no approved wording, jurisdiction, signatory or authorization was provided. Do not issue one until supplied and reviewed.
2. FPDF's standard font transliterates or omits non-Western glyphs (including Urdu/Arabic). A Unicode font/PDF renderer should be approved and tested before relying on documents for such names.
3. Document downloads are staff-only; donor self-service document download is **not** enabled because a public reference alone is not sufficient proof of identity. The donor/recipient receives attachments via email after verification.
4. Payment gateway sandbox, SMTP and real upload/restore testing require environment credentials and a staging deployment. Existing queued mail can still fail if SMTP is not configured; jobs and errors are visible in the admin queue.
5. Approval stage configuration is code/config-driven, not an admin UI. Reorder/removal of stages for in-progress records requires a planned data migration. Existing historical rows are marked `legacy` rather than retrospectively claimed verified.
6. Existing reports remain otherwise unchanged; finance totals count bank-confirmed online gifts when `status=completed`, **even if staff review remains pending**. The receipt and certificate gates require final staff verification. A change to financial recognition policy requires a separately approved accounting specification.

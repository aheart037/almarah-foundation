## Security findings and fixes in Part 7

1. `MailQueue::processJob()` formerly delivered even when another worker had already changed the job to `sending`, creating a double-send race. It now requires the atomic claim to affect exactly one row. Transport `false` is now logged as a failure, never as `sent`.
2. Queue Retry formerly accepted `sending` jobs and allowed all `logs.view` staff to resend every event. It now operates **only on failed jobs**, atomically; admin-role staff may retry; finance staff may retry donation events only; log viewers cannot retry. The button follows the same policy. POST CSRF remains mandatory.
3. The old `/admin/donations/export` silently stopped after 5,000 rows. It now writes all matching rows in private batched CSV under a read-consistent DB transaction, preserves the existing columns/filters and spreadsheet-formula escaping, deletes after serving and writes a required export audit event. A **5,010-row** integration test passed.
4. Sensitive report PDF/CSV/XLSX and staff proof/document downloads now use **required** audit writes; if the audit table is unavailable, the file is not returned (CSV/XLSX temporary files are removed). Other pre-existing audit events remain best-effort; the audit table is **not tamper-evident** against a database administrator.
5. Private document path resolution now checks a canonical location inside private storage; traversal and symlink escapes are denied. Proof download is already permission-gated, attachment-only and no-store. Upload validation requires a real uploaded file, extension/MIME agreement, size limit and image decoding or PDF header; this is not a malware scanner or a full PDF sanitizer.
6. The public donation status page no longer reveals the donor's full name or bank/provider transaction ID to a reference holder; IP-based reference lookups are throttled at 60/min. The public receipt status and amount are still shown to the holder of the reference by design. Existing short historical references remain valid.
7. Added the requested `initial_review` role as an **explicit backward-compatible alias** for existing `initial_reviewer`, including seeding, staff/permission checks, role assignment UI and report staff filters. No existing role is renamed or removed. The seeder is idempotent; run `php bin/console db:seed` after deployment to create the new role and its permissions.
8. Fundraising DB password now uses the environment secret accessor. Authentication already uses `password_hash`/`password_verify`, session ID rotation, HttpOnly/SameSite cookies and login rate limiting; public forms already use CSRF, validation, honeypots and DB-backed throttles. Financial routes use server-side permission middleware. SQL placeholders and HTML escaping were inspected and adversarially tested on representative paths; this was not a formal whole-codebase penetration test.

## Configuration and remaining limitations

- **Before production:** supply and validate environment-specific database/APP_KEY/session HTTPS settings, SMTP host/credentials/from-address and a scheduled `php bin/console mail:work --once` worker; use an isolated test recipient first. Contact/volunteer and donation email enqueue and fake-transport delivery were tested, **not actual SMTP acceptance, inbox delivery or SPF/DKIM**. Receipt/certificate email attachments were tested with a fake transport after final verification; no legal tax exemption authorization was supplied.
- Meezan and Etisalat endpoints/handoff remain present and provider-state logic was tested synthetically. **Real credentials, bank callbacks, settlement, duplicate-provider responses on a bank sandbox/live system, refund API and production reconciliation were unavailable**. Do not call these certified. The separate fundraising deployment was not available to test end-to-end campaign/fundraiser operations; local admin campaign route and report fixtures passed.
- Public status is a reference-based bearer view with masked identity; historical references have limited entropy. Do not publish reference lists. Any stronger ownership/token scheme for existing links requires an explicit compatibility plan with bank return URLs and donor emails.
- Public-facing PDFs and uploads use existing FPDF/image/MIME checks; FPDF's core fonts cannot faithfully render Urdu/Arabic; malware scanning and PDF sanitization are not implemented. The local PHP-router proof test is not proof that a particular production web server honors `.htaccess`; configure and test web-server denials for `/storage`, `/config`, `.env`, and backups at deployment.
- The current database audit is ordinary relational storage: verification events and adjustments are separate tables, but SQL administrators can change audit rows. Required export/proof audit is fail-closed; ordinary audit logging remains best-effort. External immutable audit storage/retention and backup restore drills remain operational work.
- No production database was examined. Read-only reconciliation against a sanitized production snapshot, performance under production volume, live gateway/SMTP validation, and full public/browser accessibility audits remain deployment gates.

## Rollback / recovery instructions (not executed on production)

Part 7 adds **no schema migration**. Prior V2 migrations `0010`–`0013` are additive but do not have automatic down scripts. Before deploying them, take a verified encrypted off-site backup of the database and private `storage` uploads, record the code commit, and stop writers for a consistent restore window. For example, with credentials in a `0600` file **outside the web root**: `mysqldump --defaults-extra-file=/secure/db.cnf --single-transaction --routines --triggers DATABASE > /secure/v2-before.sql`; verify backup integrity and a restore on staging. To roll back, stop web/queue workers, restore the *matching* code revision and backup (`mysql --defaults-extra-file=/secure/db.cnf DATABASE < /secure/v2-before.sql`), restore matching private files, then reconcile any payments, uploads and queued emails created after the backup before reopening. Never run these restore commands on production without a maintenance and reconciliation plan; schema downgrades alone would delete new donation-review/form history.

**Packaging gate:** Do not make a final release package until the remaining production-specific bank, SMTP, private-file web-server, backup/restore and production-data reconciliation checks have been completed by an authorized operator. No package was created in this phase.

# V3 Part 5 — Geo-IP currency selection and estimate system

**Working copy:** local `v2-delivery` (base HEAD `6be9d92`). This part builds on the uncommitted Part 4 donation form. Earlier V3 parts and their reports were preserved. **Scope decision:** the donor chose **payable currencies only**, not decorative unsupported currencies, and approved public third-party providers called from the server.

## Behavior delivered

1. On the first `/donate` visit without a saved preference, the server uses the connection's `REMOTE_ADDR` for an HTTPS country lookup with **IPWho**. Pakistan maps to PKR; US, UK, Eurozone, UAE, Saudi Arabia, Canada and Australia map to USD, GBP, EUR, AED, SAR, CAD and AUD respectively. A local currency is selected **only if a corresponding published bank account exists**. Unsupported countries/currencies, private IPs, provider errors, and unavailable data fall back to PKR. The server does **not** trust client-supplied `X-Forwarded-For` headers. Country-only results are cached in the visitor's session for 24 hours; failures for about 10 minutes. IP addresses are not written to the Geo-IP session cache.
2. An explicit currency choice always wins over the IP suggestion. The first-party `/donate/currency` POST saves the choice in the session (with CSRF validation); `?currency=USD` also works for a manual/no-JavaScript choice. Geo-IP never locks the selector. The UI tells visitors that their IP is sent to IPWho for an initial suggestion and links to its privacy policy.
3. The donation page now has a **searchable currency combobox** with flag, full name, ISO code, and symbol, plus keyboard navigation, Escape, selection state and a native `<select>` fallback when JavaScript is unavailable. The choices are PKR and supported currencies with **published** bank accounts. SAR is supported for a published Saudi-riyal bank account; it is not shown merely because it appears in an example. No unsupported foreign online gateway is advertised. The same descriptive labels appear on the transfer-report currency selector.
4. **ExchangeRate-API Open Access** supplies daily PKR-based rates. Server-side rates are cached in a locked file until the provider's next-update time; on failure, a recent cached rate may be shown for up to 48 hours **marked stale**, with a 10-minute retry backoff. If no usable rate exists, converted presets disappear, custom conversion is refused and the donor must enter an amount in the chosen currency. A visible UTC update time, estimate disclaimer and required provider attribution are displayed. The `/donate/estimate` POST produces a bounded donation **estimate**, not a raw rate table or a financial transaction; it has CSRF, payable-currency validation and per-IP throttling. Presets and custom amounts update before submission; rapid changes or user edits invalidate older in-flight estimates.
5. **Payment-currency accuracy:** Online card checkout remains PKR-only and server-rejects a forged foreign-currency online POST. Foreign-currency donation figures are explicitly *estimates*, not bank quotes. Selecting bank transfer shows an account matching the selected currency but creates **no donation or payment**. The donor transfers funds and enters the **actual transferred amount** on `/donate/transfer`; the review record stores that exact currency/minor-unit amount, still pending staff verification. No exchange rate changes a gateway charge, donor-confirmed online amount, existing ledger row, or report total. SAR can now be selected for a published bank account in the bank-account admin form, public review flow and staff offline form; reports discover distinct currencies from recorded donations.

## Providers and operating limits

- IPWho: [official API documentation](https://ipwhois.io/documentation) and [privacy policy](https://ipwhois.io/privacy). The keyless free HTTPS endpoint allows limited requests (its documentation currently says 1,000/day) and has **no uptime SLA**. Session caching reduces calls; a higher-volume deployment should arrange an appropriate plan or a local Geo-IP database. If deployed behind a reverse proxy, `REMOTE_ADDR` may be the proxy rather than the visitor; configure a **trusted** proxy/IP mechanism before expecting accurate per-donor hints. Unverified forwarded headers must not be accepted.
- ExchangeRate-API: [Open Access documentation](https://www.exchangerate-api.com/docs/free) and [terms](https://www.exchangerate-api.com/terms). The open service updates roughly daily, permits caching, requires visible attribution and explicitly describes rates as **informational/illustrative, not transaction rates**. This implementation uses them only for donor-facing estimates and never for charging or financial records.
- Operational fallbacks: `DONATION_GEO_DISABLE_REMOTE=1` and `DONATION_RATES_DISABLE_REMOTE=1` disable outbound lookups; the latter leaves manual currency selection and bank instructions functional. `DONATION_RATES_CACHE_FILE` can point to a writable private cache path. Default cache: `storage/cache/donation_rates_pkr.json` (blocked from web access by the existing router). Provider requests enforce HTTPS, TLS validation, short timeouts and no redirects. Real providers were smoke-tested using a public test IP and an informational PKR→USD quote; no donor IP or live payment was used in that check.

### Investigated failures and fixes in Part 10

1. The initial browser donation-form script used Playwright `isVisible()` on a selector matching nine seeded PKR bank cards. Changed the assertion to count visible cards; the final **46 checks pass**. This was a multi-bank fixture/test assumption, not a donor-page bank-rendering failure.
2. The first configured-gateway run was against a database left by the standalone admin-UX fixture and lacked the `general-fund` campaign, yielding “could not find that fundraiser or campaign.” Reinitialized the **disposable** database with all 17 migrations and 7 seeders; the final **15 checks pass**. No production records were altered.
3. New Part 10 browser check initially expected 403 for a CSRF-less API call; actual application response was **419**, the correct CSRF failure. Corrected test expectation.
4. New live responsive check found **53 px overflow at 320 px** on `/admin/users/create`: the long submit label could not wrap. Added a specific button class and `max-width: 100%; white-space: normal; text-align: center` in admin CSS. Full new suite then passed **81 checks**.

No known failing automated test remains in the final executed set. The above first-run failures are disclosed, not silently counted as passes.

## Outstanding blockers and production requirements

- **Payments — release blocker:** Part 6 provider integrations are still unapproved/unimplemented as required for active Stripe plus active UBL and Meezan. There is **no Stripe implementation**, and neither UBL nor Meezan has been validated against approved merchant sandbox documentation or real credentials. Confirm the organization’s registered Stripe account-country eligibility, approved gateway product/API versions, callback/webhook signatures and event semantics, merchant IDs/codes, allowed hosts, refund/cancel behavior, sandbox endpoints and test cases. Obtain credentials **through a secrets manager, not chat or source control**. Prove verified success, failure, cancellation, replay/idempotency, delayed webhook and ledger outcomes end to end before enabling gateways. Bank-transfer fallback is not proof of online processing.
- **External APIs:** Public Geo-IP and FX provider URLs, caching/fallback and IP disclosure were documented in Part 5; verify provider terms/quotas, IP/proxy trust, regional behavior, uptime and outage fallbacks from the actual deployment network. Browser tests intentionally used cached FX and no remote calls. FX figures are estimates, never payment settlement or ledger conversion.
- **Production preflight:** Install/validate Composer dependencies with the intended PHP version/extensions, supply noncommitted production `APP_KEY`, DB/SMTP/provider secrets and HTTPS/cookie/proxy settings, ensure private storage and write permissions, exercise backups and restore, perform migration backup/preflight against a **copy** of the real schema, then schedule and verify live deployment/monitoring. MySQL DDL is not automatically rolled back. Existing historical payments must not be rewritten or presumed verified. Review optional first-install lock and other residual items in `V3-PART-9-SECURITY.md`.
- **Reporting/data:** No production reports URL/error or grant records were supplied. The minimal grant register/assignments are tested locally, but production report reconciliation, real grant totals and actual user acceptance remain unverified; inventing amounts would be inappropriate.
- **Remaining QA:** Execute the absent Composer/PHPUnit tooling if required by deployment CI; test real provider sandbox outcomes with approved materials; run external-provider and production-equivalent smoke, accessibility/device/browser matrix, load and disaster-recovery tests. No claim is made that all browsers, all device sizes, all provider states or all API/console paths were exhaustively covered.

**Readiness decision:** Local regression and UI QA for the implemented V3 parts is green. **V3 as requested is blocked for production**, especially online payment integration and real-provider validation. Keep unconfigured online methods hidden and preserve bank transfer until a separately approved deployment/acceptance plan succeeds. No production change is authorized by this report.
